Capture regression - render scale slice (2026-08-11)
====================================================

The claim under test: with the settings at their defaults and the capture
harness pinning the pipeline via `setAdaptive(false, 1)`, the slice changes
nothing about what the game draws. Capture is not byte-deterministic on this
box, so the threshold is not zero -- it is the spread between two captures of
the SAME tree.


Named sources on disk
---------------------
  shots-base-71a8d3b/       baseline, captured from clean base 71a8d3b before
                            any slice code (Task 0)
  shots-base-71a8d3b-run2/  second capture of that same commit, same tree --
                            the control, i.e. the noise floor
  shots-after/              this tree (slice tasks 1-3), captured in Task 3

All three are gitignored and left on disk. The JSON manifests beside this file
are the committed evidence.


Aggregates, side by side
------------------------
  pair                                  meanDiff   pctOver8   maxOfMax
  ------------------------------------  ---------  ---------  --------
  CONTROL   base       vs base-run2         1.517      2.888       210
  AFTER     base       vs after             1.805      3.851       218
  AFTER'    base-run2  vs after             1.120      1.537       182

  manifests: diff-control.json
             diff-base-vs-after.json
             diff-base-run2-vs-after.json

Reading. The base-vs-after aggregate (1.805) sits slightly above the control
(1.517), which on its own would be ambiguous. The second base-to-after pair
settles it: measured against the OTHER base run, the after tree scores 1.120 --
below the control. The two base-to-after numbers bracket the control from both
sides (1.120 < 1.517 < 1.805). The after tree is therefore not further from
base than the two base runs are from each other; which base run you diff
against moves the number more than the slice does.

Where the difference lives, per scene, confirms the same thing. Every elevated
cell in base-vs-after is one of the five stochastic scenes that already
dominate the control -- 04-combat, 06-loaded-hud, 08-explosion, 10-inventory,
19-overkill -- all crowd and particle scenes whose frame timing varies run to
run. The static menu screens, which are exactly the frames a resolution change
could not leave alone, are unmoved:

  scene                 control mean   after mean
  15-logbook.png               0.060        0.060
  16-run-summary.png           0.035        0.035
  17-artifacts.png             0.087        0.085
  18-difficulty.png            0.120        0.119
  14-survivor-select.png       0.148        0.189

A leaked render scale resamples the whole drawing buffer; it cannot show up in
the explosion scene and skip the logbook. These five cells are the positive
evidence that the harness pin held and `_userScale` stayed at 1 through the
capture run.


Subject gates
-------------
`npm run shots -- --out shots-after` exits 1. This is pre-existing and not
caused by the slice. The subject-failure set is EXACTLY the two scenarios that
already fail at clean base (reproduced 3x at base, recorded in the slice
ledger):

  06-loaded-hud: monsters under load
  19-overkill: the launched corpse, the survivor, the corpse is off the ground
               it died on

No more, no fewer. The pass criterion for this task is set equality against the
base failure set, and it holds.
